# WB-004: Автоподписка получателей уведомлений бота

## Что происходит

Получатели уведомлений заданы переменной RESETWATCH_BOT_CHAT_IDS (WB-002).
Новый получатель попадает в рассылку только ручной правкой env на машине
алертов и рестартом сервиса. Свой chat id человек сам не увидит, а правка
env требует машинного доступа к серверу.

## Чего хотим

Бот отвечает на /start подпиской: chat id сохраняется, уведомления идут без
правки env. /stop снимает подписку. На обе команды бот отвечает
подтверждением в чат. Notify.Send идёт по объединённому списку: чаты из env
плюс активные подписчики. Подписки переживают рестарт сервиса. Сбой
доставки одному подписчику не роняет остальных, механика WB-002.

## DoD

- /start сохраняет chat id подписчика, копия каждого уведомления доходит ему
  без правки env
- /stop снимает подписку, уведомления больше не приходят
- подписки живут в SQLite и переживают рестарт
- сбой одному адресату пишется в журнал с chat id и не отменяет остальных
- выкат на машину алертов, живая проверка подписки и отписки в двух чатах

## Сценарий проверки

Сценарий исполняется после выката на машину алертов. Адрес машины лежит
в секрете INFRA_IP и в текст задачи не попадает, агентские шаги идут
через secretctl.
Живое уведомление ждём от ближайшего опроса источников, расписание 3/15.
Мой чат остаётся в RESETWATCH_BOT_CHAT_IDS, чат коллеги в env не
прописан, подписку коллеги даёт только /start.

1. systemctl is-active печатает active.
2. Я и коллега открываем бота в Telegram и шлём /start. Бот отвечает
   подтверждением подписки в каждый чат.
3. Запрос к subscribers отдаёт два chat id.
4. Человек ждёт живое уведомление. Оно приходит в оба чата, мне из env
   и коллеге, чей chat id в env не прописан.
5. Коллега шлёт /stop, бот отвечает подтверждением снятия.
6. Рестарт сервиса, после него systemctl is-active печатает active,
   а запрос к subscribers отдаёт тот же единственный chat id. Подписка
   пережила рестарт, снятая не вернулась.
7. Человек ждёт следующее живое уведомление. Мне оно приходит, коллеге
   нет.

```sh
secretctl exec INFRA_IP -- sh -c 'ssh -p 8822 -o BatchMode=yes -o ConnectTimeout=5 root@"$INFRA_IP" "systemctl is-active resetwatch"'
secretctl exec INFRA_IP -- sh -c 'scp -P 8822 -o BatchMode=yes root@"$INFRA_IP":/var/lib/resetwatch/state.db /tmp/wb004-state.db' && sqlite3 /tmp/wb004-state.db "select chat_id from subscribers order by created_at"
secretctl exec INFRA_IP -- sh -c 'ssh -p 8822 -o BatchMode=yes -o ConnectTimeout=5 root@"$INFRA_IP" "systemctl restart resetwatch && sleep 2 && systemctl is-active resetwatch"' && secretctl exec INFRA_IP -- sh -c 'scp -P 8822 -o BatchMode=yes root@"$INFRA_IP":/var/lib/resetwatch/state.db /tmp/wb004-state.db' && sqlite3 /tmp/wb004-state.db "select chat_id from subscribers order by created_at"
```

- Исключение: обкатка (агентские шаги требуют живой машины алертов
  с секретом INFRA_IP и выкаченного сервиса, шаги человека идут в живом
  Telegram; в свежем дереве с временным HOME не исполняется ничего).
